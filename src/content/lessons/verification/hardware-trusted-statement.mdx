
### 2.1.2 From a chip to a trusted statement

A machine can already prove which model it is running. That proof is the place
to start, because it is real, it is deployed, and it is narrower than it
sounds.

Tinfoil serves open-weight models inside a hardware trusted execution
environment and publishes a verification path for the claim "this endpoint is
serving exactly these weights." Its verify output puts three things in front
of a reader, and they are not equally strong.

| What the reader is shown | Who stands behind it |
| --- | --- |
| A root hash of the model weights, committed as a Merkle tree, named inside a signed attestation report | The hardware manufacturer's signing key, over the code that was loaded at launch |
| The same hash in the service's own configuration for the model it says it is serving | The operator, asserting it |
| The public release those weights were built from, which a reader can download and hash independently | Nobody. It is a fact about a public repository: checkable by anyone, attested by no one |

Remote attestation is often described as a chip proving its state. That description hides several actors, several separate judgments, and one assumption about who the enemy is.

The IETF’s Remote ATtestation procedureS architecture distinguishes three roles: an **Attester** produces evidence, a **Verifier** appraises that evidence against reference values and policy, and a **Relying Party** decides what to do with the result. This separation matters. The component that checks a signature need not be the institution that decides compliance, and neither automatically has authority to impose a consequence.

<Src>H. Birkholz et al., [“Remote ATtestation procedureS (RATS) Architecture”](https://www.rfc-editor.org/rfc/rfc9334.html) — IETF RFC 9334, January 2023.</Src>

#### The Minimum Vocabulary

**Hardware-rooted identity.** A device uses a cryptographic key and certificate, or another hardware-bound credential, to authenticate evidence. Some designs derive secrets from physical properties such as a physically unclonable function. Others provision or generate keys during manufacturing. “Hardware-rooted” does not mean literally unforgeable. It means that impersonation should require defeating a defined hardware and key-management boundary.

**Root of trust.** The component or assumption at the bottom of the chain. Other claims inherit its integrity. A root of trust may protect key use, measure boot state, verify firmware, or isolate code. A flaw at this layer can invalidate many apparently separate controls at once.

**Secure boot.** A mechanism that restricts low-level code to versions authorized by a signing policy before execution.

**Measured boot.** A mechanism that records cryptographic measurements of code or configuration as it starts. A verifier can later compare those measurements with expected values.

**Attestation evidence.** Signed claims or measurements about a device and its state. The evidence must normally include a freshness mechanism, such as a nonce or trusted time, so an old compliant statement cannot be replayed.

**Reference values and endorsements.** Information used to decide what measurements should be expected and which keys or device properties should be trusted.

**Revocation.** The ability to stop trusting a compromised key, certificate, firmware version, device, reference value, or authority.

**Appraisal policy.** The rule that turns measured facts into a result such as “acceptable for this workload.” This is a policy judgment, not a property of the signature itself.

#### The Deployed Primitive, and Who It Was Built For

The only attestation chain in production on AI accelerators is NVIDIA's, and
the engineers who built it described it in *Communications of the ACM* in
January 2024. The account is worth reading for what it says about intent. The
H100's trusted execution environment is anchored in an on-die hardware root of
trust; booting in confidential-computing mode turns on hardware protections
for the confidentiality and integrity of code and data.

Note the threat the design answers. The party being protected is the customer
renting the machine. The party being protected against is whoever holds the
machine: a compromised host, the cloud provider, an employee with physical
access. That is a sound and useful threat model, and it is the reverse of a
treaty's. Confidential computing exists so a tenant can trust a machine it
does not own. A verification regime needs a rival to trust a machine the
Prover does own. Same primitive, same signatures, opposite direction. Every
deployed guarantee in this section was built for the first case, and the
question on every page of it is what survives when the owner becomes the
adversary.

Current NVIDIA documentation describes an operational attestation chain for supported GPUs. Evidence is collected from the GPU, checked against signed Reference Integrity Measurements, evaluated locally or by NVIDIA’s Remote Attestation Service, and checked against certificate-revocation information. This is a useful deployed primitive because it makes the trust chain concrete.

It also shows why implementation details matter. NVIDIA’s Blackwell multi-GPU documentation, updated August 1, 2026, states that each GPU is attested independently and that the process does **not** attest topology or switches. Supported Hopper Protected PCIe configurations can include additional multi-GPU and NVSwitch checks. A general statement such as “GPU attestation proves the cluster configuration” is therefore false. The answer depends on the product, configuration, evidence fields, and appraisal policy.

<Src>NVIDIA, “Architecture Overview,” [*Attestation Quick Start Guide*](https://docs.nvidia.com/attestation/quick-start-guide/latest/architecture.html), current August 1, 2026; [“Blackwell Multi-GPU Attestation Example”](https://docs.nvidia.com/attestation/quick-start-guide/latest/attestation-examples/blackwell_multi_gpu.html), updated August 1, 2026; [“Hopper Multi-GPU (PPCIE) Attestation Example”](https://docs.nvidia.com/attestation/quick-start-guide/latest/attestation-examples/hopper_multi_gpu.html), current August 2026. A simplified chain looks like this:

> device and measurement component → device evidence and nonce → signing key and certificate chain → reference values and revocation data → verifier appraisal → relying-party decision → regulator or treaty response

For each link, ask:

- Who controls it?
- What can that actor falsify, suppress, delay, revoke, or refuse?
- Is cooperation legally required, technically required, or merely convenient?
- What independent evidence checks the link?
- What happens when the link fails?

#### What a Signature Does and Does Not Do

A valid signature supports a statement such as “the holder of this trusted key signed these claims.” It does not by itself establish that:

- The measurement code observed the right property;
- The measurement was complete;
- The reference value was correct;
- The evidence described the current state rather than a replayed state;
- The device remained compliant after the measurement;
- The device occupied the declared location or topology;
- No other device or workload existed;
- An institution may lawfully act on the result.

Cryptography can faithfully transmit a false or insufficient measurement. The value of attestation therefore depends on the measurement boundary and the governance of keys, reference values, updates, revocation, and decisions. Tinfoil's engineers put the general version in the sentence this page opened with: attestation measures launch state, not runtime state.

#### When the Owner Is the Adversary: A $50 Case

Researchers at KU Leuven and the University of Birmingham built Battering RAM:
an active DDR4 interposer, a custom board costing under $50, that sits between
the processor and its memory. At boot it is transparent and passes every trust
check. Switched on afterwards, it silently redirects protected addresses to
attacker-controlled locations. It breaks Intel's scalable SGX and defeats AMD
SEV-SNP attestation on fully patched systems. The schematics are open source.
The one requirement is brief physical access to the machine.

Read that requirement against the confidential-computing threat model above.
For a cloud customer, physical access is precisely what the adversary does not
have, so a memory interposer sits outside the threat model and the guarantee
holds. For a treaty verifier, physical access is precisely what the Prover
does have. The same device is irrelevant in the first case and decisive in the
second, and it costs less than dinner.

This is not an argument that attestation is useless for verification. It is an
argument about what has to be added around it: tamper-evident enclosures that
destroy keys on intrusion, physical inspection to confirm the enclosure is
intact, and evidence from outside the box that does not depend on the box's
key at all. 2.1.6 compares architectures on exactly that question.

<Src>J. De Meulemeester, D. Oswald, I. Verbauwhede, and J. Van Bulck, “Battering RAM: Low-Cost Interposer Attacks on Confidential Computing via Dynamic Memory Aliasing,” [batteringram.eu](https://batteringram.eu/), to appear at the 47th IEEE Symposium on Security and Privacy, May 2026.</Src>

#### The Adversary Changes the Assurance

<div className="trio-table">

| Prover profile | What becomes easier for the prover | What remains comparatively stronger |
| --- | --- | --- |
| **Cloud customer without physical access** | Manipulating user software, workload behavior, labels, accounts, and timing | Provider-controlled hardware, physical security, and manufacturer-backed attestation may be difficult for the customer to alter |
| **Laboratory controlling its servers** | Physical access, administrative control, optional security modes, peripherals, network routes, updates, and logging | Independent manufacturer services or separately installed sensors may still impose constraints, but must be tested against owner control |
| **State-backed owner** | Supplier pressure, substitute hardware, expensive physical attacks, coercion of domestic firms, manipulation of inspections, and long preparation | Assurance may require mutually governed keys, externally installed monitoring, supply-chain reconciliation, destructive sampling, and evidence outside the device |

</div>

The same product can be strong against a remote tenant and weak against an owner with physical access. “Secure” is not a mechanism property without an adversary.

#### The Artifact: One Attestation Result

Here is the shape of the evidence, taken from NVIDIA's own single-GPU
attestation example. The service returns a signed token whose claims include:

| Claim | What it carries | What it is evidence of |
| --- | --- | --- |
| `ueid` | A unique identifier for this GPU | Which device is speaking, inside the vendor's identity scheme |
| `hwmodel` | The hardware model, for example `GH100 A01 GSP BROM` | The part, not the part's history |
| `eat_nonce` | The nonce the verifier supplied | Freshness: this token was made for this challenge |
| `measres` | Whether measurements matched the reference values | That the firmware measured equalled what the vendor published |
| `secboot` | Whether secure boot is enabled | A configuration flag, as reported by the platform being appraised |
| `dbgstat` | Debug status, for example `disabled` | Whether a debug path was open at measurement time |
| `x-nvidia-gpu-vbios-version`, `x-nvidia-gpu-driver-version` | Firmware and driver versions | What was loaded, by version string |
| `x-nvidia-gpu-attestation-report-signature-verified`, `x-nvidia-gpu-vbios-rim-signature-verified` | Whether the report and the reference-measurement signatures checked out | That the vendor's keys signed the report and the reference values |

The appraisal can run locally or against NVIDIA's Remote Attestation Service,
which returns the token. Read the columns: every row is about the device's own
identity and launch-time state, and the right-hand column never reaches
quantity, workload, location, or authority.

<Src>NVIDIA, [“Hopper Single GPU Attestation Example”](https://docs.nvidia.com/attestation/quick-start-guide/latest/attestation-examples/hopper_single_gpu.html) and [“Architecture Overview,”](https://docs.nvidia.com/attestation/quick-start-guide/latest/architecture.html) *Attestation Quick Start Guide*, documentation current August 2026. First-party implementation documentation, not an independent adversarial evaluation.</Src>
